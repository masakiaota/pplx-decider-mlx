# 27B (Decider v1.3)

27B has 64 layers (Gated DeltaNet and full attention, same layout family as Flash) and a 51.25 GB BF16 language model. Linear layers take 66-83% of time (`E-002`), so the weight format and matmul kernel decide most of the speed.

## Earlier history (brief)

- 8-bit weights (29.4 GB) gave 100/100 on the gate but need almost twice the memory of 4-bit and were 14-17% slower. The work moved to 4-bit.
- Plain affine 4-bit and an MXFP4 variant gave 99/100. Several 4-bit formats (NVFP4, NF4, group 128, channel balancing, activation clipping) were tried and dropped: no speed gain, or more error.
- **Compensated group-64 4-bit (adopted as B015).** GPTQ-style rounding compensation on group-64 affine 4-bit weights restored 100/100 on the gate at 17.2 GB main weights with no runtime cost. With compiled long-input graphs, 5.4K tokens went 5.0 -> 3.8 s. This was the 27B default before the final round.
- A comparison with an official 27B Mac build was not possible: no official GGUF for 27B v1.2 was available to the official app.

## Row-wise 4-bit and W4A8

**W4A8 on group-64 weights (rejected).** Multiplying INT8 activations directly with group-64 4-bit weights needs a scale per 64-element group inside the matmul; the result was slower than standard MLX quantized matmul (`27b-speed/001`).

**Row-wise symmetric 4-bit with W4A8 (adopted).** Weights get one scale per output row (absmax/7), so the matmul can run fully in integers and apply scales once in the epilogue. All linear layers except k/v use it. Against B015: single 427 tokens 0.89x, 20-request list 0.83x, 5,368 tokens 0.94x; main weights 15.72 GB vs 17.20 GB. Quality was the problem: 97-99/100 on the gate, and Delta-logit standard deviation about twice B015 (0.86-1.06 vs 0.43-0.47).

**Compensation with the original calibration (partial).** Adding GPTQ-style compensation to the row-wise weights cut layer error by about 41% but the gate stayed at 98/100 (`27b-speed/002`). That calibration used 1,062 tokens taken from the first four gate questions, which both overlapped the evaluation and was far too small for K = 5,120-17,408.

**Recalibration (adopted, `D-001`, `D-002`).** A new calibration pool of about 240K tokens (BoolQ train, SQuAD v2 train, Qasper train, SQuAD Locate requests) with no overlap with any evaluation set, checked mechanically. Findings:

- More calibration data lowers held-out layer error steadily (0.57 -> 0.43 of the uncompensated error from 1K to 169K tokens), and the best damping moves from 0.3 to 0.01. The large damping that looked optimal before was a symptom of too little data.
- Act-order and a per-row scale search (MSE) lower it further to 0.29, about half of the old setting. Neither changes the stored format.
- Including Locate inputs in calibration lowers Locate-input error in layers 0-7 by 4-17% without hurting BoolQ.

Results with the recalibrated weights: gate 100/100 under single, list-separate and list-isolated (was 98/98/98), max |dp| 0.27 (was 0.42); binary agreement with BF16 718/726, same as B015. Mean |dp| is still slightly above B015 (0.0189 vs 0.0156, +0.0038 [+0.0013, +0.0067]).

**s4 kernel (adopted, `E-004`).** The W4A8 kernel used unsigned 4-bit weights and a large tile for `down`. Storing the 4-bit codes as two's complement (XOR 0x88888888 on the packed words) lets the hardware's int8 x int4 path compute the same integer sums, and a measured per-shape tile table fixes the tile choice. Outputs are bit-exact with the unsigned version; time is 0.87-0.97x. The recoded files are stored on disk, so no 12 GB recode happens at load. Details in [kernels.md](kernels.md).

**Unified entry (adopted, `B-004`).** Before, Locate still went through the group-64 weights, so both weight sets had to be mapped. Every feature now goes through the row-wise W4A8 weights, with the Locate LoRA added on top; the group-64 copies of replaced layers are not mapped. Mapped memory including Locate went from 19.08 to 16.67 GB, MLX peak from 20.7-20.9 to 18.3 GB, and the first request in a process from 4.84 s to 0.64-0.80 s (with runtime-M kernels).

Other rejected items: embedding table in 8-bit (agreement drops), concatenating LoRA A matrices (no gain).

## Locate

Recalibrated weights changed the Locate picture several times; later measurements on more questions replace earlier ones.

- The first row-wise weights pushed span scores down systematically (signed bias -0.125, span agreement 243/300 vs B015 280/300). The cause was the weight quantization, not the W4A8 path or BF16 LoRA (`B-013`, `C-007`).
- With recalibrated weights the bias is gone (signed -0.004), span agreement 267/300, gold F1 0.697 (BF16 0.685, B015 0.681) (`L-006`).
- **Locate-only W4A16 (rejected).** Skip activation quantization during Locate, reusing the same 4-bit codes: 274/300, no extra weights, but Locate 12-42% slower.
- **W4A16 plus B015 input projections (rejected).** 277/300, equivalent to B015, but +2.83 GB and 11-38% slower Locate.
- **FP32 LoRA (rejected).** No quality gain on top of W4A16, and Locate 36-58% slower.

The shipped engine keeps W4A8 with a BF16 LoRA. Agreement with the original model on Locate is below B015; agreement with gold labels is at the original model's level.

## Audit and serving changes

The 27B engine received the same audit as Flash (14 items, `U-002`): max length 32,768; stored temperature 1.2264 when omitted; the no-argument default had silently used the older weights and unsigned kernel and now uses the recalibrated s4 weights; HTTP layer added; memory settings that existed in two places reduced to one; research switches and dead paths removed. Length buckets (inputs up to 512 tokens), bulk packing, listen-first startup and 8-lane DeltaNet were ported from Flash. With buckets and bulk turned off, outputs are bit-exact with the overnight candidate (772/772 evaluation requests, 20/20 feature cases).

Known issue kept from earlier versions: if the very first image a process sees is a synthetic image, later image outputs change (also present in B015; cause not found). Warm-up therefore contains no image step.

**Long-input compile threshold.** Measured on fresh lengths, compile is slower than eager between about 1,000 and 2,000 tokens (trace cost) and faster above 4,096 tokens (0.63-0.81x). The threshold stayed at 4,096. Extending buckets to 513-4,096 tokens could give a further 6-8% and was not implemented.

## Final engine

Recalibrated row-wise 4-bit weights in s4 form, W4A8 for all features, BF16 Locate LoRA, long-input compile up to 32K, buckets for inputs up to 512 tokens, bulk packing, 8-lane DeltaNet, listen-first startup.

| Case | B015 (previous default) | Overnight candidate | Final |
|---|---:|---:|---:|
| Single 427 tokens (warm) | 0.294 s | 0.237 s | 0.218 s |
| 20-request list | 2.54 s | 1.95 s | 1.91 s |
| Long 5,368 | 3.18 s | 2.65 s | 2.62 s |
| Long 32.4K (HTTP) | — | 35.7 s | 21.8 s |
| 520 mixed requests over HTTP | — | 126.5 s | 116.2 s |
| 772 evaluation requests in bulk | — | 184 s (sequential) | 131 s |
| Start to first answer (HTTP) | — | 8.29 / 5.16 s | 3.31 / 3.20 s |

The "Final" column is the research engine. The release package gives the same outputs; its long inputs are 4-6% slower (32.4K: 22.86 s) and it answers the first request 0.6-1.0 s after process start ([docs/models.md](../docs/models.md)).

Quality: gate 100/100 under four conditions (99/100 on the list path with bulk disabled). Paired difference against the overnight candidate is not significant (mean |dp| +0.0011 [-0.0005, +0.0027]). Against B015 the error is higher (+0.0049 [+0.0022, +0.0079]) while decision agreement is equal; the difference comes from the 4-bit row-wise weights. On the 964-question harness: binary 717/726, choice 161/164, score argmax 70/74, Locate spans 100/114 (overnight candidate 96/114).

Memory: 16.67 GB mapped including Locate; MLX peak 23.7-25.0 GB at 32K tokens (25.03 GB for Locate + binary on 32K); RSS about 2 GB because weights are memory-mapped. The original BF16 model peaks at 57.1 GB.

## Open items

- The non-compiled single and batch paths still spend 11-19% in element-wise ops and kernel launches.
- Locate linear layers run at about 78 TFLOP/s; about 40% of Locate time is still recoverable in principle.
- The image-order dependence above is unexplained.
